# Initial hero and development-harness intent review

Decision status: accepted by the repository owner on 2026-10-12.
Prepared on: 2026-10-12.
Branch: codex/adlc-review-fixes.

The repository owner accepted the seven requirements below as the intended
behavior of the local portfolio showcase. The decision was the explicit chat
response "I accept" to this seven-requirement review packet. Their existing 25
acceptance scenarios remain the behavior contract. Product acceptance establishes what to maintain;
it does not assert that tests were executed or that a production deployment is
ready. The reviewed PR becomes the merged baseline.

| Requirement | Accepted intent | Scope and limits |
| --- | --- | --- |
| [REQ-SHELL-001](../REQ-SHELL-001.md) | Signed-in navigation respects roles and remote availability; unavailable/opt-in modules explain their state | Navigation visibility is a UI contract, with API authorization reviewed separately |
| [REQ-IDENTITY-001](../REQ-IDENTITY-001.md) | Unique usernames, matching passwords of at least eight characters, regular-user registration with a cart, login/logout cookies, and administrator-only item mutations | This is the local showcase identity contract; acceptance does not certify production authentication security |
| [REQ-WORKSPACE-001](../REQ-WORKSPACE-001.md) | Users manage their own notes/files; note descriptions stay below 1,000 characters; valid files are non-empty, at most 2,000,000 bytes, and have a filename unique to that user | Ownership and validation remain explicit acceptance boundaries |
| [REQ-COMMERCE-001](../REQ-COMMERCE-001.md) | Authenticated catalog/cart/order flows, personal cart/order ownership, and administrator catalog maintenance | The shell clears the cart after recording checkout; payment processing and atomic concurrent checkout are outside these scenarios |
| [REQ-CHAT-001](../REQ-CHAT-001.md) | Create/join shared rooms by code, broadcast live messages, and disable sending while disconnected | The directory is derived from sender message records; a room code is not a claim of private-room membership or per-room authorization |
| [REQ-VEHICLES-001](../REQ-VEHICLES-001.md) | Vehicle list/map with location and price enrichment; administrator maintenance through the map UI | The role scenario covers map controls; backend mutation authorization is not established by that UI scenario, and persistence remains demo-local |
| [REQ-HARNESS-001](../REQ-HARNESS-001.md) | Read-only Jira intake, stable requirement/scenario links, isolated proposals, and generated cases reviewed with implementation | Mapped acceptance scenarios cover fixture intake; live-adapter transport tests are separate; Jira mutations require exact human approval |

The complete wording and scenarios in each linked requirement are part of this
decision. Code-derived provenance stays recorded after acceptance.

The other seven requirements remain proposed: Jira, ChatLLM, MLOps, Petstore,
AI operator console, RAG, and application AI approvals. They need their own
product decisions. In particular, MLOps and RAG describe access-control boundaries
that need separate security review; they are not included in this approval.

The accepted requirement revisions are listed by SHA-256 in
requirements/baseline.json. The source gate rejects stale or unrecorded accepted
revisions. Draft cases remain generatable and testable, with proposed status
visible in reports. Promotion of a selected requirement requires accepted intent
and passing native evidence. Agents must not infer acceptance from a green test run.
